## 1. A tiny example first

Here is a complete test program, three instructions long:

```
addi x1, x0, 5      # x1 = 0 + 5
addi x2, x1, 1      # x2 = x1 + 1 = 6
ecall               # stop
```

`x1` and `x2` are two of the CPU's 32 registers, its small set of built-in variables.
`x0` is a register that always holds zero. Chapter 02 explains all of this. For now,
read the program as three lines of very simple code.

This is what the project does with it:

1. **Encode.** Python turns each line into a 32-bit number, the *machine code* a CPU
   actually reads. `addi x1, x0, 5` becomes `0x00500093`. The encoder lives in
   `model/encoder.py:34-100`.
2. **Load.** The three words are written into the instruction memory of a simulated
   computer (`tb/tb_top.sv:36`). The same words are given to a Python program that
   imitates a perfect RISC-V CPU, the **golden model** (`model/iss.py`).
3. **Run the hardware.** A simulator executes the CPU design, written in the hardware
   description language SystemVerilog. Every time the CPU *finishes* an instruction, it
   reports what it did on a set of output wires called the **retire port**. For example:
   "pc = 0, instruction 0x00500093, wrote register x1 = 5".
4. **Run the model one step.** For each report, the testbench asks the golden model to
   execute one instruction too. The model says: "pc = 0, instruction 0x00500093, wrote
   x1 = 5".
5. **Compare.** The two reports must be identical, field by field. If they are, go on to
   the next instruction. If not, stop and print exactly what differed.
6. **Final check.** After `ecall`, the testbench also compares all 31 writable registers
   and every word of data memory between hardware and model.
7. **PASS** if nothing differed.

That's the whole idea. The rest of the project makes it thorough:
- many more programs;
- programs that are hard for a CPU;
- a second, much more complicated CPU;
- measurements of what was tested.

## 2. What the project builds

**Two CPUs** that run the same instruction set, **RV32I**: the 32-bit base integer
instructions of RISC-V, an open instruction set used in industry and teaching (chapter 02).

| Core | File | How it works | Why it exists |
|---|---|---|---|
| Single-cycle | `rtl/core_single.sv` | Each instruction is fetched, executed and finished in one clock cycle | Simple enough to get right first; a stepping stone |
| 5-stage pipeline | `rtl/core_pipe.sv` | Like a factory line: up to 5 instructions are in progress at once, each in a different stage | How real CPUs get a faster clock; much harder to get right (chapter 05) |

Both cores share five building blocks:
- `rtl/decoder.sv`: understands instructions;
- `rtl/alu.sv`: does arithmetic;
- `rtl/regfile.sv`: holds the 32 registers;
- `rtl/branch_unit.sv`: decides branches;
- `rtl/lsu.sv`: prepares loads and stores.

**A verification environment** that proves the cores behave like the golden model:
- **directed tests:** hand-written programs;
- **the official RISC-V test suite** (*riscv-tests*);
- **two C programs**, compiled with GCC;
- **constrained-random programs:** randomly generated, but always legal;
- **functional coverage:** a record of which interesting situations actually happened;
- **mutation analysis:** deliberately breaking the pipeline to show the tests notice.

**Measurements:**
- test pass counts;
- coverage;
- **CPI**, cycles per instruction, the cost of the pipeline's stalls;
- the size of each core after **synthesis**, the translation of the design into real
  logic gates.

All of them are regenerated by one command, `make results` (`Makefile:102-112`).

## 3. Why this is harder than "the program printed the right answer"

Picture a pipeline bug: when an instruction needs a value the previous instruction just
computed, the CPU sometimes reads the old value instead. What happens with an ordinary
test program?

- **The bug might never fire.** The program may never have that exact pair of
  instructions back to back.
- **The bug might fire harmlessly.** The wrong value may be overwritten before anything
  uses it.
- **The bug might fire much later.** It may show up only as a wrong final answer
  thousands of cycles later, with no clue where it came from.

So this project checks **every retired instruction** against the model, not just the final
answer, and generates many programs designed to create those back-to-back dependencies.

The cost of checking that way is a golden model you can trust. That's why the model is
tested first and independently (chapter 06).

## 4. The full flow, from `make test` to PASS

The sequence below is what really happens when you type `make test`. The two simulations
(one per core) are just the same steps run twice.

```mermaid
sequenceDiagram
    autonumber
    participant You
    participant Make as make (Makefile)
    participant Pytest as pytest
    participant Runner as cocotb_runner.py
    participant Verilator
    participant Sim as Simulator process
    participant Test as test module (cocotb)
    participant H as CoreHarness
    participant ISS as Python ISS

    You->>Make: make test
    Make->>Pytest: pytest tests/model (pure Python, 429 tests)
    Make->>Pytest: pytest tests/rtl
    Pytest->>Runner: test_core_directed[single], [pipe], ...
    Runner->>Verilator: build tb_top + core (+ -DPIPELINED for pipe)
    Verilator-->>Runner: compiled simulator in sim_build/tb_top_<core>/
    Runner->>Sim: start it with +CORE=<core>
    Sim->>Test: cocotb imports the test module, runs each @cocotb.test
    Test->>H: load(program, data)
    H->>Sim: write imem / dmem through VPI
    H->>ISS: same image into the model's memory
    loop every clock cycle (falling edge)
        H->>Sim: read rvfi_valid and the retire port
        alt an instruction retired
            H->>ISS: step()
            ISS-->>H: expected Retire record
            H->>H: compare; mismatch -> ScoreboardMismatch
        end
    end
    H->>H: compare all registers and all data memory
    Sim-->>Runner: results file (JUnit XML)
    Runner-->>Pytest: fails if any cocotb test failed
    Pytest-->>You: N passed / failed
```

Where each step lives:

| Step | Code |
|---|---|
| `make test` = `test-model` + `test-rtl` | `Makefile:66-72` |
| pytest entry point per suite and core | `tests/rtl/test_core_directed.py:414-416` |
| Build with Verilator, run with cocotb | `tests/rtl/cocotb_runner.py:28-60` |
| Choose the core at build time | `tb/tb_top.sv:49-53` |
| One cocotb test per directed case | `tests/rtl/test_core_directed.py:391-411` |
| Load the program into the RTL memories and the ISS | `tb/harness.py:116-134` |
| Reset and clock | `tb/harness.py:136-144` |
| The per-cycle loop | `tb/harness.py:148-202` |
| The per-instruction comparison | `tb/harness.py:221-236` |
| The end-of-test comparison | `tb/harness.py:238-247` |

## 5. What a failure looks like

To see the checking work, the project can inject a bug on purpose. `make waveform` removes
the pipeline's load-use stall (chapter 05) and runs one test. The scoreboard stops at the
first wrong instruction:

```
retire #2 mismatch at pc=0x00000008: add x3, x2, x0
  rd_wdata   core=0x00002000  model=0x00000007
```

That is real output from this repository. It says:
- the third instruction to finish (counting from 0), `add x3, x2, x0` at address 8,
  wrote the wrong value into x3;
- the core wrote `0x2000`;
- the model says it should be `7`.

The tool also draws the waveform of those cycles, `docs/img/failing_waveform.png`.
Chapter 05 explains why the value was wrong.
